## 1. 사건과 증거

예약 운용 첫 실전에서 GPU 드라이버가 리셋되며 MuMu 인스턴스 2개가 사망했고,
스캔은 그것을 **인지하지 못한 채 3~4시간 헛돌다** 청크를 "완주" 처리했다.

| 시각 | 사건 | 근거 |
|---|---|---|
| 00:07:35 | 두 파트 정상 재개(용스 94행 / 실버 313행), 약 18분 정상 스캔 | 로그 헤더·진행 로그 |
| **00:24:36** | nvlddmkm 오류 Id 14 | 시스템 이벤트 |
| **00:25:16~17** | nvlddmkm 오류 Id 153 ×3 (GPU 장치 리셋) | 시스템 이벤트 |
| 00:24~00:25 | 용스 행 109·110 추적 손실 — **팬 #4·#5의 측정값이 완전히 동일**(-1591, -1713, -1900) = 프레임 정지 | part1 로그 |
| 00:25~03:22 | 용스: 남은 **161행 전부 실패**(마커 0.09) 후 **exit 0**으로 종료 | part1 로그 |
| 00:26~04:27 | 실버: **219행 전부 실패**(마커 0.17) 후 `DXGI_ERROR_DEVICE_REMOVED` 예외 | part2 로그 |
| 결과 | 수집 161,954/2,624,400타일(6.2%). **체크포인트는 청크 끝(272/544)까지 전진** — 380행이 미스캔 상태로 "완주" 위장 | DB 조회 |

데이터 오염은 없었다(지연 기록 설계가 미보정 버퍼를 전량 폐기, PK 중복 0).
피해는 **시간 손실**과 **체크포인트 무결성 훼손**이다.

## 2. 결함 3가지 (근본 원인)

**결함 1 — 캡처 정지가 침묵한다.** `WgcCapture.grab_fresh()`는 새 프레임이
도착하지 않으면 2초 후 **조용히 낡은 프레임을 반환**한다(`capture.py:95`
`return self.grab()`). GPU가 사라져 콜백이 멈춰도 호출자는 정상 프레임을 받은
것으로 오인한다. Watchdog은 빈·검은 프레임과 크기 변경만 보므로 **정지된
정상 이미지는 통과**시킨다.

**결함 2 — 연속 행 실패에 중단 조건이 없다.** 행 실패는 "보충 대상"으로만
기록되고 다음 행으로 넘어간다. 380행이 연속 실패해도 스캔은 계속된다.

**결함 3 — 실패한 행도 체크포인트를 전진시킨다.** `set_checkpoint(row.index + 1)`이
성공·실패와 무관하게 실행된다. 청크 실행(`--end-row`)은 보충 방문도 건너뛰므로
이 행들은 회수 경로가 없다.

## 3. 임계값의 실측 근거

전 실행 로그를 집계했다. 정상 구간과 사고 구간이 명확히 분리된다.

| 구간 | 연속 행 실패 최대 | 연속 무진행(신규 0타일) 행 최대 |
|---|---|---|
| 정상 운용 전체(ac03 6회·병렬 2계정·무인 실증·RDP 실증) | **0** | 0~2 |
| 예약 운용 정상 구간(part1 run1~3 = 115행, part2 run1~2 = 45행) | **1**(고립 — 행 19·24·56·92·272) | **5** (북서 경계 판독 취약 구간) |
| **사고 구간** | **161 / 219** | **162 / 219** |

- 연속 **실패** 임계 **5회**: 정상 최대 1회의 5배 여유. 사고는 약 5.5분 만에 감지.
- **무진행** 행 수는 임계로 쓰지 않는다 — 정상 최대가 5로 높고, 무엇보다
  **이미 커버된 영역의 멱등 재실행에서 전 행이 무진행**이라 오탐한다(§5 대안 c).
- 캡처 무프레임 임계 **연속 3회(약 6초)**: 30fps 기준 약 180프레임 결손에 해당.

## 4. 제안 변경

### 변경 1 — 캡처 생동 감지 (`win/capture.py`, 근본 원인 지점)

`grab_fresh()`가 시간 초과로 낡은 프레임을 반환할 때 연속 횟수를 센다. 새
프레임을 받으면 0으로 초기화한다. 연속 3회면 `CaptureStalled` 예외를 던진다.

```text
CaptureStalled(RuntimeError)  # "캡처 프레임 정지 6.0s — 대상 렌더링 중단(창 종료·GPU 리셋)"
```

이 예외는 **행 단위 복구 대상이 아니다** — 재시도해도 캡처는 살아나지 않는다.
행 재시도 루프를 통과해 스캔 전체를 중단시킨다(아래 변경 3).

### 변경 2 — 연속 행 실패 중단 (`controller.py`)

행 루프가 연속 실패 횟수를 센다. 성공(예외 없이 반환)하면 0으로 초기화한다.
연속 **5회**면 스캔을 중단한다. 사유는 로그와 요약에 남긴다.

### 변경 3 — 중단 시 체크포인트 되돌리기 (`controller.py`)

중단할 때 체크포인트를 **연속 실패가 시작된 행**으로 되돌린다(캡처 정지로
중단하면 진행 중이던 행). 다음 실행이 그 행부터 다시 시도한다.

**고립 실패는 기존 동작을 유지한다** — 체크포인트를 전진시키고 보충 방문에
맡긴다. 영구 불량 행 하나가 스캔을 영원히 가로막지 않게 하기 위함이며,
이는 승인된 설계 v3 §4.3의 판단을 그대로 보존하는 것이다.

중단된 스캔의 DB 상태는 기존 어휘 그대로 **`paused`**(재개 가능)를 쓴다.
스키마·상태 어휘 변경은 없다.

### 변경 4 — 중단의 가시화 (`cli.py`, 운용)

중단으로 끝난 스캔은 CLI가 사유를 출력하고 **종료 코드 2**를 반환한다
(정상 0, 예기치 못한 예외 1). 스케줄 태스크의 "마지막 결과"와 래퍼 로그의
`=== 종료 (exit 2) ===`에 비정상이 드러난다. **이번 사고에서 용스가 exit 0으로
끝난 것이 인지 지연의 직접 원인이었다.**

보충 방문 단계도 같은 중단 조건을 따른다(중단 시 잔여 미커버는 다음 실행 몫).

### 범위 밖 (조사 결과 불필요)

- **시작 시 대상 생존 확인**: 사고 직후 결함 후보로 꼽았으나, `find_mumu_instance`가
  인스턴스 부재 시 이미 명시적 오류로 실패한다(`session.py:103`). 남는 구멍은
  "창은 있으나 렌더링이 죽은" 경우뿐이며 변경 1이 그것을 덮는다. 별도 점검 추가 안 함.
- **GPU 드라이버 리셋 자체의 예방·자동 복구**: 하드웨어·드라이버 영역이며
  본 작업 범위 밖. 스캔 재시작은 스케줄러의 다음 실행이 담당한다.

## 6. 영향 범위

- **요구사항:** 신규 요구 없음. NFR-03과 예외 표의 미구현 구간을 채운다.
  인수 조건 3건(AC-D1~D3)을 추가한다.
- **설계:** §2 win 계층(캡처 생동 계약), §4.3 스캔 루프(중단 조건·체크포인트),
  §4.4 이상 감지. 격자·재앵커·팬 추적·분류는 불변.
- **구현:** `win/capture.py`, `controller.py`, `cli.py`. PC 경로·MuMu 경로 공통.
- **데이터:** 스키마 불변, 마이그레이션 없음. 상태 어휘 불변(`paused` 재사용).
- **공개 인터페이스:** `scan` 종료 코드에 2(중단)가 추가된다. 인자 변경 없음.
- **하위 호환:** 기존 DB·명령 그대로 동작. 되돌리려면 임계 상수를 무한대로
  두면 기존 동작과 동일(즉시 롤백 가능).
