# ADR-004: 스캔 모드 확장 구조 — 전략 패턴 + 공통 파이프라인

- 상태: 제안
- 날짜: 2026-08-01
- 관련 변경 요청: 사용자 결정 Q-01(3개 모드 지원, v1은 MODE-A만 구현)

## 배경

사용자는 화면인식 전체 스캔(MODE-A), 하이브리드(MODE-B), 영역 한정 전수 클릭(MODE-C)을 모두 지원하되 v1은 MODE-A만 구현하기로 결정했다. 후속 모드 추가가 기존 코드의 구조 변경 없이 가능해야 한다.

## 고려한 대안

1. **전략 패턴:** `ScanMode` 인터페이스(방문 계획 생성 + 방문 지점 처리)를 모드별로 구현하고, 이동·캡처·인식·저장 서비스는 공유.
2. **단일 스캐너 + 모드 분기 플래그** — 분기 누적으로 후속 모드 추가 시 회귀 위험.
3. **모드별 독립 프로그램** — 공통 코드 중복, 데이터 스키마 분화 위험.

## 결정

1안. v1은 `FullSpriteScan`만 구현하고 `HybridScan`/`RegionClickScan`은 인터페이스와 스텁만 둔다. 클릭 판독 전용 서비스(PopupReader)는 인터페이스만 정의한다. 데이터 스키마(tiles)는 3개 모드의 필드를 처음부터 포함하며(레벨 컬럼은 MODE-B/C 전용으로 MODE-A에서 NULL), `scans.mode`로 스캔 단위 구분한다.

## 이유

- 모드 간 차이는 "어느 좌표를 방문해 무엇을 읽는가"에 국한되므로 전략 경계가 자연스럽다.
- 스키마를 선제 통합하면 후속 모드 추가 시 데이터 마이그레이션이 불필요하다.

## 결과와 단점

- v1에 사용되지 않는 NULL 컬럼·스텁이 존재한다 — 후속 확장의 명시적 자리표시로 수용한다.
- MODE-B의 "선별 기준"(어떤 타일을 클릭할지)은 본 ADR 범위 밖이며 후속 설계에서 결정한다.
