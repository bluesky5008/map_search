# ADR-005: 클라이언트 창 크기·종횡비 정책 — 넓고 낮은 창으로 설정

- 상태: 승인 (2026-08-02, 기준선 v2)
- 날짜: 2026-08-02
- 관련 변경 요청: [DCR-001](../changes/DCR-001-mode-a-zoom-limits.md)
- 관련 요구사항: NFR-01, NFR-02

## 배경

기준선 v1은 "클라이언트 창 크기 1282x752 고정"을 전제로 캘리브레이션하도록 정했다. 스파이크 S-2b/S-2c 실측에서 이 전제가 성능상 크게 불리함이 드러났다.

게임은 월드 렌더 배율을 **창 높이**에 맞춘다. 따라서 화면에 보이는 타일 수는

```
가시 타일 수 ≈ W·H / a²   (a = 타일 스텝 픽셀, a ∝ H)
            ∝ W / H       (즉 종횡비)
```

로, **창 크기가 아니라 종횡비에 비례**한다. 실측(모두 디테일 줌 최대 축소, 클릭 좌표 판독 기준):

| 클라이언트 | 종횡비 | 타일 스텝 a | 가시 타일 |
|---|---|---|---|
| 1278x719 | 1.78 | 104 px | 85 |
| 2544x1401 | 1.82 | 200 px | 89 |
| **2544x657** | **3.87** | **82 px** | **246** |

종횡비를 유지한 확대는 효과가 없고(85→89), 사분면 스냅으로 종횡비를 3.87로 만들면 약 2.9배가 된다.

## 고려한 대안

1. **시작 시 창을 넓고 낮은 크기로 설정(SetWindowPos)** — 스캔 소요를 1/3로 줄인다. 사용자의 창 배치를 변경하므로 종료 시 복원이 필요하다.
2. **v1 전제 유지(고정 크기 1282x752)** — 사용자 창을 건드리지 않지만 스캔이 3배 오래 걸린다.
3. **사용자가 수동으로 창을 배치하고 도구는 검증만** — 도구가 창을 바꾸지 않지만 매 실행마다 수작업이 필요하고 오설정 위험이 있다.

## 결정

1안. WindowSession이 스캔 시작 시 대상 창을 **설정된 스캔 창 크기**로 `SetWindowPos`하고, 종료 시 원래 위치·크기로 복원한다.

- 기본값: 대상 모니터 작업 영역의 사분면 크기(예: 5120x1392 → 2560x696). 종횡비가 3 이상이 되도록 한다.
- 사용자가 설정으로 크기를 지정할 수 있게 한다.
- 시작 시 실제 클라이언트 크기를 읽어 그리드 캘리브레이션에 반영한다. **고정 크기를 코드에 상수로 두지 않는다.**
- 창 조작에는 관리자 권한이 필요하다(ADR-002의 전제와 동일).
- 스캔 종료·중단·오류 시 원래 창 배치를 복원한다(복원 실패도 로그로 남긴다).

## 이유

- 스캔 소요가 32~52시간에서 10~15시간으로 줄어 MODE-A2의 실용성이 결정적으로 달라진다.
- 창 조작은 이미 보유한 권한(관리자)과 API(SetWindowPos)로 가능하고, 되돌릴 수 있다.
- 크기를 설정값으로 두면 다른 해상도·모니터 구성에서도 동작한다.

## 결과와 단점

- 스캔 중 사용자의 창 배치가 변경된다 — 시작 시 안내하고 종료 시 복원하는 것으로 완화한다.
- 타일이 작아져(스텝 82px, 타일 폭 약 165px) 인식 난도가 소폭 상승한다. 스프라이트 분류에는 충분한 크기지만, 분류 정확도(NFR-04) 검증은 실제 스캔 창 크기에서 수행해야 한다.
- 스냅 상태에서는 디테일 줌의 축소 여유가 없다(한 노치 더 축소하면 전략 뷰로 전환). 줌 제어는 "디테일 최종 단계"를 목표로 정확히 맞춰야 한다.
- 창 크기를 바꾸면 게임이 UI를 재배치하므로, HUD 오클루전 영역도 창 크기에 따라 다시 산출해야 한다.
